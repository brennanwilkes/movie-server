## 1. BPP+ source-pinning correction — APPLIED AND LIVE

Brennan clarified that "nothing in the UI changed" was the wrong call: he wants the *number itself* as

So the correction now feeds the live number. **Easy Rider went 78 → 66 and moved from `warn` to
`bad`**, which is what he said it should have read all along. The Apartment 58 → 44.

### How it works
`complexityForKey()` in `probe.js` multiplies the measured complexity by `biasFactor(R)`. That is the
single place it is applied, and every BPP+ inherits it because `bppTargetFor()` reads it and
`bppIndex()` reads that — for rows AND candidates, so a row and its suggestions stay on one scale and
**no ranking changes** (Easy Rider's best candidate moved 142 → 120 alongside it).

Also corrected, so the library does not run two scales at once:
- `globalComplexity()` — the median every unprobed film falls back to.
- `cxOf()` in the shrinkage ladder — a sibling measured from a starved copy would otherwise drag an
  estimate down by the very bias being removed.

### The fit (live, refits itself)
```
R0.00-0.30 x1.75(n=5)   R0.30-0.40 x1.75(n=17)  R0.40-0.50 x1.40(n=32)
R0.50-0.70 x1.40(n=19)  R0.70-1.00 x1.24(n=4)   R1.00-1.20 x1.07(n=1)   R>=1.20 uncorrected
```
Fitted from the 78 monotonic banked pairs, **not hardcoded** — `_biasFit` is invalidated whenever
`setEntry()` banks a new pair, so it sharpens on its own as Brennan replaces films. Exposed as
`pinningCorrection` on `/api/probe` for reports.

Three guards, and **two of them were live bugs for one deploy** — check them if the numbers ever look
wrong:
- `BIAS_MIN_N = 8`. Undersampled buckets are not applied raw. The `R 1.00-1.20` bucket has n=1 and its
  raw median (×1.39) was *higher* than the better-sampled bucket below it (×1.24).
- **Monotone non-increasing in R.** More headroom cannot mean more under-measurement.
- **Gap fill by POSITION, not by carrying a neighbour.** The first attempt carried, and broke both
  ends: the most-starved bucket (n=5) fell through to ×1.00 — no correction for the worst files — while
  R 0.70–1.20 inherited the low-R factor and over-corrected nearly-transparent films. Now: below the
  lowest fitted bucket take that factor; above the highest, interpolate down to exactly 1.0 at
  `BIAS_R_TRUST`. Sanity check that it works: the interpolated 1.24 for R 0.70–1.00 matches that
  bucket's own observed median exactly.

### Known limits (do not forget these)
- **It is a FLOOR.** 56 of the 96 corrected films still have R < 1, so the better copy was itself
  pinned and one round under-corrects. Easy Rider lands at 66; Brennan's eye said 40–60.
- `correlation(R, log F) = -0.158` — R reliably identifies **that** a measurement is pinned but
  predicts **how much** only weakly.
- No pairs exist above R 1.2 (you only re-download bad films), so that range is uncorrected by
  construction rather than by evidence.

## 4. QUEUED WORK ITEM #1 (agreed): store the per-sample probe values

`controller/scripts/probe-film.sh` collects every per-sample bitrate in `$KLIST`, passes it into awk
as fields `18..NF`, uses it **only** to compute `spreadRatio = hi/lo`, and then throws it away:

```awk
for (j=18; j<=NF; j++) { v=$j+0; if (lo==0 || v<lo) lo=v; if (v>hi) hi=v }
spread = (lo>0) ? hi/lo : 0;
```

**Why it matters more than sample count.** `complexity` is the **mean** of the samples, but visible
artifacts appear in the **hardest** scenes. Median spread is 4.0×, p90 is 9.2× — so the mean
systematically under-targets a film's demanding shots. That is very plausibly what Brennan saw on
Easy Rider: shimmer on grain-heavy flat walls, i.e. the expensive tail, not the middle.

Storing the per-sample values (a) lets mean-vs-percentile be re-decided later **with no re-probe**,
(b) gives a real standard error instead of `bpp-recheck.sh`'s range-to-sigma approximation, and
(c) identifies *which* sample is the outlier in the 13 broken-spread films.

Same shape of mistake as the discarded priors — capture it now, decide later.

**Do this BEFORE any deep re-probe pass, or the pass has to be run twice.**

## 5. QUEUED WORK ITEM #2 (agreed, Brennan's design): weighted nightly re-probe ordering

> "after it has finished probing films that have never been probed before, it goes film by film in a
> weighted ordering and reprobes to fill in new data where it needs it or where it guesses that it
> would be worth it to reprobe"

Current behaviour (`nextUnit()` in `probe.js`): never-measured first, then stale, and as of tonight
stale gets a guaranteed 1-in-4 share so it can no longer be starved. There is **no weighting beyond
that** — the stale pool is sorted by key (movies before TV).

### Signals available for the weighting, all already recorded per film
| signal | meaning | where |
|---|---|---|
| `unitStale()` | the file changed since measurement | `probe.js` |
| `R` (= fileBpp/complexity) | **< 1 ⇒ measurement was source-pinned, target is a floor** | cache |
| `spreadRatio` | hardest sample / easiest — sampling untrustworthiness | cache |
| `priors.length` | how much calibration history the film already has | cache (new) |
| beloved / Top-100 | declared intent — worth more accuracy | Radarr profile / playlist |

### Suggested priority order (to be refined)
1. Never measured.
2. **Broken measurements** — `spreadRatio > 25` (13 films today, worst is `Blade Runner: Black Out
   2022` at **1279×**; one sample 1279× another makes the mean meaningless).
3. Stale (file changed) — banks a calibration pair, which is the scarce resource.
4. High `spreadRatio` **and** `R >= 1.2` — the only population where deeper sampling actually helps
   (see the numbers below); ideally re-probed at 32 samples, not 8.
5. Beloved / Top-100 with a wide error band.

### The measured case for targeting rather than re-probing everything
| | share | |
|---|---:|---|
| bias dominates — needs a better *source*, sampling will not help | **79%** | median 11 pts |
| noise dominates — more samples **would** help | **21%** | median ±6 pts |

For the **162 films with R ≥ 1.2** (probe had headroom, so no bias) sampling noise is the *only*
error: **median ±12.8 pts, worst ±77**. That is the population worth deep-sampling.

Cost: `8→16` halves nothing much (±4.2), `8→32` gives ±3.0 at 800 s/film = **18 films/night**, so
162 films ≈ **9 nights** inside the existing 240 min/night budget. Exactly the "slowly over the
weeks" shape Brennan described.

## 7. UI clutter removed from the Upgrade tab — and one stale number it was hiding

Brennan, 2026-08-12: "basically all of the + and - badges, theyre clutter." So **`gainPills()` is gone
entirely** — no more `+ Remux-1080p source`, `+ DTS`, `+ 310 bpp+`, `+ plays on more devices`,
`− PS4 transcodes` on the Upgrade **row**.

Safe because the row was the only caller and every fact was already on screen twice: the size and
BPP+ deltas sit two spans to its left, and the candidate **cards in the sheet** render source, audio,
device support, formats and seeders per candidate. The row was duplicating its own sheet.

It had also become actively WRONG, which is what prompted the look. `gains` is a list of baked
**strings** inside the cached verdict, so once the source-pinning correction went live the pills kept
serving pre-correction figures while the delta beside them was re-derived at serve time by
`rescoreCand()`:

| film | row delta | stale pill |
|---|---|---|
| I Saw the Devil (2010) | 49 → **262** | + 310 bpp+ |
| Fast Five (2011) | 76 → **167** | + 186 bpp+ |
| The Host (2006) | 57 → **71** | + 84 bpp+ |

**THE SERVER STILL COMPUTES `gains`/`losses` AND MUST KEEP DOING SO.** `rankCands` drops a candidate
with `if (!gains.length) drop(r, 'nothing measurably better than what is on disk')` — they are
load-bearing as a **filter** even though nothing renders them, and they stay on the API for reports.
Do not "clean up" the server side.

**The tradeoff this accepts:** losing the loss pills gives up the "tradeoffs allowed but labelled"
property from 2026-07-30. A candidate costing a PS4 audio transcode no longer says so *on the row* —
it says so on its card in the sheet, which is where the choice is actually made. Revisit if a bad swap
ever gets picked because the row looked like an unqualified win.

**General hazard, still live:** any human-readable string baked into a cached verdict goes stale when
the scoring changes underneath it. `gains`/`losses` were the only ones; anything similar added later
must be re-derived at serve time the way `bppPlus`/`bppBand`/`cfBlocked` already are.
